# Защита ЛР5: шпаргалка

Тема: создание датасета из сырых данных стороннего сервиса и его анализ.

## Рассказ на минуту

В материалах к работе пример разбирает сырой журнал `watcher.csv` сторонней программы. Я взял другой
сторонний источник: открытый API Hacker News. Скриптом собрал 8000 историй за девять дней, разобрал
сырой JSON в таблицу из 16 столбцов, проверил качество, построил графики и сохранил в csv.
Сайт живёт по американскому рабочему дню, пик в 15 часов UTC. Внимание распределено крайне неравномерно:
медиана 2 очка, но 4,2 % историй набирают сотню и больше. Для демонстрации обучил модель предсказывать,
наберёт ли история 10 очков. Результат честно отрицательный: ROC-AUC 0,57, популярность почти
не зависит от метаданных публикации.

## Этапы

**Источник.** Официальный API Hacker News отдаёт записи по одной, поэтому для сбора взял API поиска
Hacker News: 1000 историй за запрос. Без авторизации.

**Сбор.** 8 запросов, каждый следующий ограничен временем самой старой истории предыдущего.
Сырой ответ 3,5 МБ сохранён в файл без текстов историй (в одной был чужой ключ доступа, GitHub блокировал загрузку), повторный запуск берёт его, а не сеть.

**Структурирование.** Время → дата, час, день недели. Ссылка → домен. Теги → тип истории.
Заголовок → длина. Автор → хеш.

**Очистка.** Пропусков, дубликатов и пустых заголовков нет, удалять ничего не пришлось.

**Результат.** `data/hn_stories.csv`, 8000 строк, 16 столбцов, 931 КБ.

## Числа

- 8000 историй, 19–28 сентября 2026 года, в среднем 934 в день.
- Пик в 15 ч UTC (558), минимум в 3 ч UTC (186). Будни 992 в день, выходные 586.
- Очки: медиана 2, максимум 1803, 28,1 % только голос автора, 4,2 % от 100 очков.
- 63 % историй без комментариев. Корреляция Спирмена очков и комментариев 0,526.
- github.com 818 историй (10,2 %), всего 3915 доменов.
- 4533 автора, 80,7 % с одной историей, половину историй дают 703 автора.
- Модель: 7196 историй старше суток, популярных 13,9 %. Лес ROC-AUC 0,571,
  логистическая регрессия 0,573, полнота популярных 0,506 и 0,665.

## Вероятные вопросы

**— Почему модель такая слабая? Датасет плохой?**
Датасет в порядке, это вывод о предметной области. Популярность на Hacker News решают первые голоса
в ленте новых историй и содержание заголовка. Время публикации, тип истории и прошлые успехи автора
почти ничего не дают. Следующий шаг: признаки из текста заголовка, как в ЛР2.

**— Почему ROC-AUC, а не accuracy?**
Популярных историй 13,9 %. Ответ «всегда нет» даёт accuracy 0,86 и при этом бесполезен.
ROC-AUC и полнота по популярным это показывают.

**— Зачем веса классов?**
Без них модель выгоднее всего отвечает «нет» на всё, так и было в первой версии.
Веса делают ошибку на редком классе дороже.

**— Почему разбиение по времени?**
Модель должна предсказывать новые публикации. Случайное разбиение подмешало бы в обучение истории
из будущего, в том числе историю авторов и доменов.

**— Почему только истории старше суток?**
Свежие истории ещё набирают очки. История, опубликованная час назад с 2 очками, может к вечеру
набрать сотню, её метка ещё не окончательная.

**— Почему поиск, а не официальный API?**
Официальный отдаёт по одной записи, для 8000 историй нужны десятки тысяч запросов.
API поиска отдаёт тысячу за раз.

**— Чем это похоже на пример из материалов?**
Там журнал активности программы: время, приложение, заголовок окна. Здесь журнал активности сайта:
время, автор, заголовок. Путь одинаковый: сырой формат → таблица → категории → графики активности.

## Мини-глоссарий

- **API**: интерфейс программы для обращения других программ, здесь запросы по HTTP с ответом в JSON.
- **JSON**: текстовый формат вложенных словарей и списков.
- **Пагинация**: получение данных частями, страница за страницей.
- **UTC**: всемирное координированное время, без часового пояса.
- **Хеш**: короткая строка, однозначно полученная из имени, но не позволяющая восстановить его.
